# Waterfall Guard – Complete Task List

## 1. Repository and Architecture Audit
1. Preserve the original GitHub repository baseline.
2. Record the current Git branch, commit, and development history.
3. Verify the GitHub repository against both hosted dashboard entry points.
4. Identify outdated, missing, or inconsistent files.
5. Audit the existing application architecture.
6. Map existing code to patent requirements E3, E4, E5, and E6.
7. Identify implemented, partially implemented, placeholder, and missing functionalities.
8. Prepare a Patent Architecture Compliance Matrix.

## 2. E3 – Transaction-Specific Lifecycle Reconstruction
9. Identify existing encounter, charge, claim, acknowledgment, and remittance data models.
10. Implement relationships between encounters, charges, claims, acknowledgments, and remittances.
11. Implement the `ACCEPTED` relationship state.
12. Implement the `REJECTED` relationship state.
13. Implement the `UNRESOLVED` relationship state.
14. Implement quarantine for unresolved relationships.
15. Validate lifecycle relationship mapping using synthetic or mock data.
16. Test incorrect, missing, duplicate, and conflicting relationships.

## 3. E4 – Expected-Successor Testing
17. Identify expected successor relationships in the claim lifecycle.
18. Implement detection of missing claims.
19. Implement detection of delayed claims.
20. Identify potentially orphaned claims before payer filing deadlines.
21. Implement timely filing deadline tracking when data is available.
22. Classify actionable claims.
23. Classify expired claims requiring audit review.
24. Test missing, delayed, actionable, and expired claim scenarios.
25. Verify that unresolved relationships do not produce unsupported findings.

## 4. E5 – Read-Only Analytical Architecture
26. Audit the application for claim-modifying functionality.
27. Identify existing claim submission and write-back components.
28. Document existing operational execution dependencies.
29. Remove or disable operational claim-modifying functions from the analytical application, following the approved architecture.
30. Configure read-only database permissions.
31. Configure restricted database credentials.
32. Implement appropriate network-level access restrictions.
33. Enforce read-only restrictions at the application level.
34. Verify that the analytical engine cannot independently submit or modify healthcare claims.
35. Test read-only enforcement and unauthorized write attempts.

## 5. E6 – Separate Controlled-Execution Architecture
36. Identify existing E6-related execution and write-back components.
37. Document their purpose, dependencies, and current location.
38. Identify components that must remain outside the analytical environment.
39. Prepare a proposed separation or modification plan.
40. Document proposed permanent removals or modifications before implementation.
41. Preserve the original code and Git history for patent review.
42. Verify that execution and write-back functionality is not deployed in the analytical environment.
43. Document the final separation between analytical and controlled-execution components.

## 6. AWS IAM Security
44. Verify the existing AWS IAM developer account.
45. Review the developer's assigned permissions.
46. Configure the required minimum permissions.
47. Activate MFA for the developer account.
48. Verify that unauthorized AWS resources cannot be accessed.
49. Document the completed IAM security configuration.

## 7. Separate Supabase Development Environment
50. Verify the separate Supabase development project.
51. Configure development-specific environment variables and credentials.
52. Create or configure the required development database schema.
53. Populate the database with synthetic healthcare data.
54. Configure login functionality using synthetic data.
55. Test authentication and authorization.
56. Verify isolation between development and production environments.
57. Confirm that development testing does not access or modify production data.

## 8. Epic Integration and Mock Testing
58. Audit the existing Epic integration code.
59. Review the existing FHIR client and API configuration.
60. Prepare mock Epic/FHIR responses and synthetic claim data.
61. Test encounter and claim data retrieval.
62. Test lifecycle relationship reconstruction.
63. Test missing and delayed claim detection.
64. Test API errors and authentication failures.
65. Verify read-only behavior during integration testing.
66. Document integration test results.
67. Defer real hospital integration testing until authorized access is available.

## 9. AI Data Flow and Security
68. Identify the proposed AI features and their purpose.
69. Map data sources and destinations in the proposed AI workflow.
70. Identify the data that would be sent to the AI provider.
71. Assess potential exposure of PHI and sensitive healthcare information.
72. Define data minimization and de-identification requirements.
73. Document API authentication and secret management.
